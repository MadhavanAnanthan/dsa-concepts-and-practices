## What This Chapter Is Really About

The chapter teaches a mental habit: data system architecture is mostly about trade-offs, not universal best choices. A data system that is excellent for one workload, organization, cost model, or legal environment may be poor for another.

The chapter introduces the vocabulary needed for the rest of the book and compares four major design choices:

- Operational systems versus analytical systems.
- Cloud services versus self-hosting.
- Distributed systems versus single-node systems.
- Business goals versus legal and social responsibility.

The main message is: understand the workload, the people using the system, the operational context, and the risks before choosing an architecture.

## Data-Intensive Applications

A data-intensive application is one where data management is a primary engineering challenge. The hard part is usually not just computation. The hard part is storing large data volumes, processing them, handling changes, maintaining consistency under failures and concurrency, and keeping services available.

Common building blocks include:

- Databases: store data so it can be found later.
- Caches: remember expensive results and speed up reads.
- Search indexes: support keyword search and filtering.
- Stream processing: react to events and changes as they occur.
- Batch processing: periodically process large accumulated datasets.

Real systems often combine several of these tools using application code. The difficulty is not merely learning each tool, but deciding which tools fit the task and how to combine them when one system alone is insufficient.

Mental model: a data-intensive application is like a city infrastructure plan. A database is not the whole city; it is one part of roads, utilities, traffic control, emergency services, and public records. Architecture is the design of how those pieces cooperate.

## Frontends, Backends, And Data Infrastructure

The chapter clarifies frontend and backend terminology.

A frontend is client-side code, such as browser code or mobile app code. It mainly handles the user interface and sometimes stores data locally on the user device.

A backend is server-side code that handles user requests. It is usually reachable over HTTP or WebSocket. Backend application code reads and writes data in databases and may use caches, message queues, search systems, or other infrastructure.

Backend code is often stateless: after handling one request, it forgets request-specific state. Anything that must persist must be stored either on the client or in server-side data infrastructure.

Why the backend is harder: one frontend usually handles one user's data, but the backend manages data for all users and must handle shared infrastructure, concurrency, failures, security, and scale.

## Operational Systems Versus Analytical Systems

The chapter separates two broad categories of data systems.

Operational systems are where data is created and modified. They include backend services and the databases used by applications serving users. Application code reads and changes data based on user actions.

Analytical systems serve business analysts and data scientists. They usually contain a read-only copy of operational data and are optimized for analysis rather than user-facing updates.

Different people use these systems:

- Backend engineers build and operate user-facing services.
- Business analysts use data to create reports and support management decisions.
- Data scientists find insights, build ML/AI features, create recommendations, predict risk, rank search results, and detect spam or abuse.
- Data engineers connect operational and analytical systems and maintain data infrastructure.
- Analytics engineers transform and model data to make it useful for analysts and data scientists.

Important distinction: analysts and data scientists usually analyze data generated by users and backend services; they generally do not modify the original operational data, except perhaps to fix mistakes. They may create derived datasets.

## OLTP Versus OLAP

The chapter uses OLTP and OLAP to describe common access patterns.

OLTP means online transaction processing. In this chapter, transaction is used loosely for low-latency reads and writes. OLTP systems usually fetch a small number of records by key, known as point queries. They insert, update, or delete records based on user input.

OLAP means online analytical processing. OLAP queries usually scan many records and compute aggregates such as count, sum, or average. They support analysis questions such as revenue by store, sales changes during promotions, or products commonly bought together.

Comparison:

- OLTP read pattern: point queries for individual records.
- OLAP read pattern: aggregate over many records.
- OLTP write pattern: create, update, delete individual records.
- OLAP write pattern: bulk import through ETL or event streams.
- OLTP human user: end user of a web or mobile application.
- OLAP human user: internal analyst doing decision support.
- OLTP machine use: checking whether an action is authorized.
- OLAP machine use: detecting fraud or abuse patterns.
- OLTP query style: fixed queries predefined in application code.
- OLAP query style: arbitrary ad hoc exploration by analysts.
- OLTP query volume: many small queries.
- OLAP query volume: fewer but more complex queries.
- OLTP data meaning: latest current state.
- OLAP data meaning: history of events over time.
- OLTP dataset size: often gigabytes to terabytes.
- OLAP dataset size: often terabytes to petabytes.

Why users usually cannot run arbitrary SQL against operational systems:

- They might access or modify data they should not access.
- They might write expensive queries that harm performance for other users.
- Operational systems are designed around fixed application queries.

Analytical databases normally allow arbitrary SQL or dashboard-generated queries because exploration is the goal.

The chapter also mentions product analytics or real-time analytics systems, such as Pinot, Druid, and ClickHouse. These support analytical workloads inside user-facing products. They ingest data in real time and optimize for low-latency analytical queries.

## Data Warehousing

Historically, the same databases were used for both transactions and analytics because SQL is flexible. But in the late 1980s and early 1990s, companies increasingly separated analytics from OLTP systems by creating data warehouses.

A large enterprise may have many operational systems: customer-facing websites, checkout systems, inventory systems, vehicle routing, supplier management, employee administration, and more. Each system may be managed independently.

Directly querying operational systems for analytics is undesirable because:

- Relevant data may be spread across many operational systems, creating data silos.
- OLTP schemas and layouts are often not ideal for analytics.
- Analytical queries can be expensive and can hurt performance for normal users.
- Operational systems may live in protected networks that analysts cannot directly access.

A data warehouse is a separate database that analysts can query without affecting OLTP operations. It contains read-only copies of data from many operational systems.

ETL means extract, transform, load:

- Extract data from operational databases using dumps or update streams.
- Transform the data into an analysis-friendly schema and clean it.
- Load the data into the warehouse.

ELT is a variation where data is loaded first and transformed inside the warehouse.

External SaaS products can also feed the warehouse. Since you usually cannot access their underlying databases directly, ETL must use vendor APIs. Connector services such as Fivetran, Singer, or Airbyte can implement this movement.

## HTAP And Why Warehouses Still Matter

HTAP means hybrid transactional/analytical processing. It tries to support OLTP and analytics in one system without separate ETL.

The chapter's caution is that many HTAP systems still internally combine an OLTP system and a separate analytical system behind one interface. So the OLTP-versus-OLAP distinction remains useful.

HTAP does not replace data warehouses because enterprises often have many operational databases but want one place where analysts can combine data across systems. HTAP is most useful when one application needs both:

- Low-latency reads and updates of individual records.
- Analytical queries over many rows.

Fraud detection is given as an example where such mixed needs can appear.

Broader principle: as workloads become more demanding, systems become more specialized. General-purpose systems are comfortable at smaller scale, but larger scale often pushes architecture toward systems optimized for particular workloads.

## From Data Warehouse To Data Lake

A data warehouse usually uses a relational model queried with SQL, often through BI tools. This fits many business analyst workflows but may be less suitable for data scientists.

Data scientists may need to:

- Transform rows and columns into numerical features for ML models.
- Perform feature engineering.
- Use NLP to extract meaning from text such as product reviews.
- Use computer vision to extract structure from images.
- Work with Python libraries such as Pandas and scikit-learn, R, or distributed analytics frameworks such as Spark.

A data lake is a centralized repository that stores copies of useful data from operational systems. Unlike a warehouse, a data lake stores files without forcing one file format, schema, or data model.

A data lake can contain:

- Database records, such as Avro or Parquet files.
- Text.
- Images and videos.
- Sensor readings.
- Sparse matrices.
- Feature vectors.
- Genome sequences.
- Any other data useful for analysis.

The advantage is flexibility. A data lake can store raw data and allow each consumer to transform it into the form needed for their work. The chapter calls this the sushi principle: raw data is better.

Data lakes are often cheaper than relational storage because they can use commodity object storage.

## Beyond The Data Lake

As analytics matures, organizations pay more attention to DataOps: the management, governance, operations, privacy, and compliance of analytical systems and data pipelines.

Analytics is also no longer only file-based or table-based. Increasingly, analytical data is available as streams of events. Batch analysis can rerun periodically, such as daily, but stream processing can react within seconds.

Fast stream processing is useful for time-sensitive work such as identifying and blocking fraud or abuse.

Sometimes analytical outputs are sent back into operational systems. This is sometimes called reverse ETL. Example: an ML model trained in the analytical environment is deployed into production to generate user-facing recommendations. Tools such as TFX, Kubeflow, and MLflow can help deploy ML models.

## Systems Of Record And Derived Data

A system of record, also called a source of truth, stores the authoritative version of data. New facts are first written there. Each fact is represented exactly once, typically in normalized form. If another system disagrees with the system of record, the system of record is correct by definition.

A derived data system is produced from another system by transforming or processing existing data. If derived data is lost, it can be recreated from the original source.

Examples of derived data:

- Caches.
- Denormalized values.
- Indexes.
- Materialized views.
- Transformed representations.
- ML models trained on datasets.

Derived data is redundant because it duplicates information, but it is often essential for fast reads and for viewing data from different perspectives.

Analytical systems are usually derived data systems because they consume data created elsewhere. Operational services may include both systems of record and derived systems. For example, an operational service may have a primary database as its system of record and indexes or caches as derived data.

The tool itself does not decide whether something is a system of record or derived data. A database is just a tool; the distinction depends on how your application uses it.

Engineering implication: if one system derives data from another, you need a process to update derived data when the original changes. Many databases assume your application uses only that one database, making multi-system integration difficult. Data pipelines help compose multiple systems.

## Cloud Versus Self-Hosting

This section frames cloud adoption as an outsourcing decision: should the organization build or buy, operate internally or use a vendor?

Rule of thumb:

- Keep work in-house when it is a core competency or competitive advantage.
- Outsource work that is non-core, routine, or commonplace.

There is a spectrum:

- Bespoke software written and operated in-house.
- Off-the-shelf open source or commercial software that you self-host.
- Self-hosted software on your own hardware or on cloud VMs.
- Managed cloud services.
- SaaS products accessed only through a web interface or API.

Deployment tooling such as Kubernetes matters, but the chapter does not focus on it because other decisions have greater influence on data system architecture.

## Pros And Cons Of Cloud Services

Using a cloud service means outsourcing operation of that software to the provider.

Potential benefits:

- Faster adoption when your team does not already know how to run the system.
- Less low-level administration work.
- Provider may have deep operational expertise from serving many customers.
- Easier scale-up and scale-down when demand varies.
- Helpful for analytical workloads where large bursts of compute may be needed briefly.

When self-hosting may be cheaper:

- Your team already has the operational expertise.
- The workload is predictable.
- You can keep purchased machines highly utilized.

Cloud services are especially useful for variable workloads. If you provision for peak load on your own machines, resources may sit idle most of the time. Cloud lets you return unused resources.

Main downsides of cloud services:

- Lack of control over missing features.
- Waiting on the provider during outages.
- Harder debugging when internals, logs, and OS metrics are unavailable.
- Vendor changes, shutdowns, price increases, or product direction can force migration.
- Vendor lock-in is worse when there are no standard APIs.
- Political sanctions or country-level conflicts can block access.
- You must trust the provider with security, privacy, and compliance.

Cloud is popular and important, but it will not replace all in-house systems. Older systems may predate cloud, and specialized requirements may still require in-house control. Very latency-sensitive systems, such as high-frequency trading, may need full hardware control.

## Cloud Native System Architecture

Cloud native means the architecture is designed to take advantage of cloud services, not merely moved onto cloud VMs.

Cloud-native systems can offer advantages such as:

- Better performance on the same hardware.
- Faster failure recovery.
- Fast scaling of compute resources.
- Support for larger datasets.

Examples from the chapter:

- Self-hosted OLTP: MySQL, PostgreSQL, MongoDB.
- Cloud-native OLTP: AWS Aurora, Azure SQL DB Hyperscale, Google Cloud Spanner.
- Self-hosted OLAP: Teradata, ClickHouse, Spark.
- Cloud-native OLAP: Snowflake, Google BigQuery, Azure Synapse Analytics.

Self-hosted software typically assumes generic resources: CPU, RAM, filesystem, and IP networking. On cloud infrastructure, you can run this kind of software on VMs, but you still administer it yourself.

Cloud-native services build higher-level systems out of lower-level cloud services. For example, object storage services such as S3, Azure Blob Storage, and Cloudflare R2 store large files and hide the physical machines. Other services, such as Snowflake, can build on object storage.

Design principle: higher-level abstractions are easier if your needs fit the use case they target. If they do not fit, lower-level components may be necessary.

## Separation Of Storage And Compute

Traditional architecture often places storage and computation on the same machine: disks plus CPU and RAM. RAID can protect against disk failure by maintaining redundant copies across disks attached to that machine.

In cloud-native systems, local disks attached to compute instances are often treated as ephemeral caches, not durable long-term storage. If the instance fails or is replaced, the local disk can become inaccessible.

Cloud providers offer virtual disks such as Amazon EBS, Azure managed disks, and Google persistent disks. These emulate block devices and allow traditional disk-based software to run in the cloud. But because the block device is implemented by a networked service, every I/O operation is effectively a network call, which adds overhead and sensitivity to network glitches.

Cloud-native services often avoid virtual disks and use dedicated storage services optimized for particular workloads:

- Object storage is good for durable large files.
- Databases may store smaller values in specialized services and larger data blocks in object storage.

This separates or disaggregates storage from compute. S3 stores files, but analysis code must run somewhere else, requiring data movement over the network.

Many cloud-native systems are also multitenant: one service and shared hardware serve several customers. This improves utilization, scalability, and provider management, but requires careful isolation so one customer cannot harm another customer's performance or security.

## Operations In The Cloud Era

Traditional roles included DBAs and sysadmins. More recent practice integrates software development and operations through DevOps. Google's version of this idea is SRE.

The purpose of operations remains:

- Reliably deliver services to users.
- Configure infrastructure.
- Deploy applications.
- Keep production stable.
- Monitor and diagnose reliability problems.

In self-hosted systems, operations often includes machine-level work such as capacity planning, provisioning machines, moving services between machines, and applying OS patches.

Cloud services hide many individual-machine details behind APIs. Storage becomes metered billing rather than fixed disks. High availability may be provided even when individual machines fail.

DevOps/SRE emphasizes:

- Automation and repeatable processes.
- Ephemeral VMs and services instead of long-running servers.
- Frequent application updates.
- Learning from incidents.
- Preserving organizational knowledge when people change.

Cloud changes operations but does not remove it. Customers still need operations work, but it shifts toward:

- Choosing suitable services.
- Integrating services.
- Migrating between services.
- Managing cost.
- Understanding quotas and resource limits.
- Maintaining application and library security.
- Managing interactions between services.
- Monitoring load and diagnosing performance or outages.

Capacity planning becomes financial planning. Performance optimization becomes cost optimization.

## Distributed Versus Single-Node Systems

A distributed system is a system in which several machines communicate over a network. Each participating process is a node.

Reasons to use distribution:

- Inherent distribution: multiple users on separate devices must communicate over a network.
- Requests between cloud services: data stored in one service and processed in another must cross the network.
- Fault tolerance and high availability: multiple machines provide redundancy when one machine, network, or datacenter fails.
- Scalability: load can be spread when one machine cannot handle the data or computation.
- Latency: serving users from geographically closer regions reduces network travel time.
- Elasticity: resources can scale up and down with demand.
- Specialized hardware: different components can use hardware that fits their workload, such as disk-heavy object storage, CPU/memory-heavy analytics, or GPU-based ML.
- Legal compliance: data residency rules may require data to stay in particular jurisdictions.
- Sustainability: workloads may run where and when renewable electricity is available or the grid is less strained.

These reasons apply to both custom application services and off-the-shelf systems such as databases.

## Problems With Distributed Systems

Distribution has costs.

Every network request can fail. A service may be overloaded, crash, or fail to respond. If a request times out, the caller may not know whether the request was received. Retrying may not be safe.

Network calls are also much slower than function calls inside one process. For large data volumes, moving computation to where the data already lives may be faster than moving the data to another machine. More nodes are not automatically faster; the chapter notes that a simple single-threaded program on one computer can sometimes beat a cluster with over 100 CPU cores.

Troubleshooting is harder. When the system is slow, the problem may be in any service or network path. Observability is the discipline of collecting and querying execution data to diagnose both high-level metrics and individual events. Tracing tools such as OpenTelemetry, Zipkin, and Jaeger help track client-server calls and their durations.

Consistency is harder. Databases provide mechanisms for consistency, but when each service owns its own database, maintaining consistency across services becomes the application’s responsibility. Distributed transactions can help, but they are rare in microservices because they reduce service independence and are not supported by all databases.

Practical conclusion: doing a task on one machine is often simpler and cheaper. Modern CPUs, memory, and disks have become larger, faster, and more reliable. With single-node databases such as DuckDB, SQLite, and KuzuDB, many workloads can run on one node.

## Microservices And Serverless

The common way to distribute a system is to divide it into clients and servers that communicate over the network, usually HTTP. A process may be both a server for incoming requests and a client for outgoing requests.

Service-oriented architecture, later refined into microservices, decomposes a complex application into services. Each service should have a well-defined purpose, expose an API, and have a team responsible for it.

Advantages of microservices:

- Services can be updated independently.
- Teams coordinate less.
- Hardware resources can be assigned per service.
- Implementation details are hidden behind APIs.
- Service owners can change internals without affecting clients.
- Each service can own its own database, avoiding a shared database becoming a hidden shared API.

Why sharing databases between services is risky:

- The database structure effectively becomes part of the API.
- Schema changes become harder.
- One service's queries can hurt another service's performance.

Costs of microservices:

- More infrastructure for deployment, scaling, logs, monitoring, health checks, and alerting.
- Harder local development and testing because dependent services must run too.
- API evolution is difficult because clients depend on fields and behavior.
- API compatibility problems may appear late in staging or production.
- Standards such as OpenAPI and gRPC help describe and manage APIs.

Core insight: microservices are mainly a technical solution to a people problem: letting teams move independently. They make sense in larger organizations but can be unnecessary overhead in smaller organizations.

Serverless, or function as a service, outsources infrastructure management to a cloud vendor. The provider allocates and frees resources based on incoming requests. Billing is based on code execution time rather than pre-provisioned instances.

Serverless tradeoffs:

- It reduces explicit capacity provisioning.
- It may impose execution time limits.
- It may restrict runtime environments.
- It can suffer slow starts.
- It is not literally serverless; code still runs on servers, possibly different servers each time.
- The word serverless is also used by infrastructure services such as BigQuery or Kafka offerings to mean autoscaling plus usage-based billing.

## Cloud Computing Versus Supercomputing

Cloud computing is not the only model for large-scale systems. High-performance computing, or supercomputing, has different priorities.

Differences:

- Supercomputers focus on computationally intensive scientific workloads such as weather forecasting, climate modeling, molecular dynamics, optimization, and partial differential equations.
- Cloud computing typically serves online services and business data systems requiring high availability.
- Supercomputers often run large batch jobs and checkpoint periodically. If a node fails, the workload may stop, the node may be repaired, and computation may restart from the last checkpoint.
- Cloud services generally cannot stop the whole system because they must keep serving users.
- Supercomputers often use shared memory and RDMA for high bandwidth and low latency, assuming high trust among users.
- Cloud environments often involve mutually untrusting tenants, so they need resource isolation, encryption, and authentication.
- Cloud datacenter networks often use IP/Ethernet and Clos topologies for high bisection bandwidth.
- Supercomputers may use specialized topologies such as multidimensional meshes and toruses for known communication patterns.
- Cloud nodes may be spread across geographic regions, while supercomputer nodes are usually close together.

Large-scale analytical systems may share some characteristics with supercomputing, but the book mainly focuses on continually available services.

## Data Systems, Law, And Society

Data architecture is shaped not only by technical goals but also by organizations, people, law, and society.

Systems that store data about people raise special concerns. Regulations such as GDPR, CCPA, and the EU AI Act affect how personal data can be stored and used.

Even outside direct regulation, data systems can affect society. Social media can influence how people consume news and form political opinions. Automated systems may affect loans, insurance, hiring, or criminal suspicion.

Engineers share responsibility for considering ethical impact and legal compliance. They do not all need to become legal experts, but they need basic awareness, just as they need basic distributed systems knowledge.

Legal requirements can create hard technical questions. Example: GDPR gives people a right to erasure, but many data systems use immutable append-only logs. This raises questions:

- How do you delete data from a structure designed not to change?
- How do you delete data that has been incorporated into derived datasets?
- How do you handle data used to train ML models?

The chapter says there are not yet clear technology-specific guidelines for GDPR compliance. Laws define high-level principles rather than mandating specific technologies, because technologies change.

## Data Minimization And Compliance Costs

Data is stored because its value is expected to exceed its costs. But cost is not just the storage bill. Costs include:

- Liability if data leaks.
- Reputational damage.
- Legal costs and fines if processing is noncompliant.
- Safety risks if governments or police compel data handover.

Some data can expose people to real harm. The chapter gives examples where stored data could reveal criminalized behavior, such as homosexuality in several countries or seeking an abortion in some US states. Location data or IP address logs can reveal sensitive movements.

After considering these risks, it may be better not to store some data at all.

Data minimization, also called Datensparsamkeit, means collecting and keeping only the data necessary for specified purposes. This conflicts with the "big data" habit of storing lots of data speculatively in case it becomes useful later.

GDPR supports data minimization: personal data should be collected only for a specified, explicit purpose, not later reused for another purpose, and not kept longer than necessary.

Businesses also respond to privacy and safety pressure. Payment processors must follow PCI standards and undergo audits. Software vendors may need SOC 2 compliance and third-party audits.

Final principle: balance business needs with the needs and rights of the people whose data is collected and processed.

## Chapter-Level Memory Hooks

Use these hooks to remember the chapter quickly:

- OLTP is the live application world: many small, predefined reads and writes.
- OLAP is the analysis world: fewer complex queries scanning historical data.
- A warehouse is the analyst-friendly relational analysis store.
- A lake is the flexible raw-data store.
- A system of record is authoritative; derived data is rebuildable.
- Cloud is outsourcing plus elastic economics, but with reduced control.
- Cloud native means building on cloud primitives, not just running old software on VMs.
- Distributed systems help with availability, scale, latency, elasticity, hardware specialization, law, and sustainability, but they add failure modes, latency, observability problems, and consistency challenges.
- Microservices reduce team coordination by increasing system coordination.
- Serverless changes capacity planning into usage-based execution, but does not remove servers.
- Legal and ethical constraints are architecture constraints, not afterthoughts.

## Interview Perspective

If asked "When should we use a distributed system?", answer with tradeoffs:

Use it when the system is inherently distributed, must survive machine or datacenter failure, must exceed one machine's capacity, must serve global users with low latency, must scale elastically, must use specialized hardware, must satisfy data residency, or can optimize energy usage by placement and timing.

Avoid rushing into it when one machine can handle the workload, because network calls fail, retries can be unsafe, debugging is harder, consistency is harder, and operational complexity rises.

If asked "Why separate OLTP and OLAP?", answer:

They serve different users, workloads, query patterns, schemas, and performance needs. OLTP protects user-facing performance and security with predefined point queries and updates. OLAP supports analysts with large scans, aggregates, and ad hoc queries over historical data. Separating them prevents analytics from damaging operational performance and allows each system to optimize for its own workload.

If asked "What is the difference between a system of record and derived data?", answer:

The system of record is the authoritative source where facts are first written. Derived data is generated from existing data, such as indexes, caches, materialized views, transformed representations, and trained models. Derived data can be rebuilt from the source, but keeping it up to date requires data pipelines or other propagation mechanisms.

## Final Takeaways

- Architecture is a set of tradeoffs, not a search for one perfect answer.
- Workload shape matters: point reads, updates, scans, aggregates, event streams, and ML all push architecture differently.
- Specialization increases as scale and workload demands increase.
- Cloud changes both economics and technical architecture.
- Distributed systems are powerful but costly; use them when their benefits outweigh their complexity.
- Data engineers must consider law, ethics, privacy, deletion, and data minimization as real design constraints.
